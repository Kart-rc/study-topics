Understand the idea · 4 min

A train ticket says 10:00 even when the train reaches the platform at 10:07. If a report uses 10:07 as its boundary, seven minutes of data move into a different run.

A scheduler answers which interval owns the data. Compute startup answers only when this attempt began. Keep those clocks separate. Pass an explicit half-open window such as [09:00, 10:00) into the transform, persist it with the run, and reuse it on retry.

A worked example

The hourly payments job is scheduled for 10:00 but starts at 10:07. It must still read events with event_time >= 09:00 and event_time < 10:00. A retry at 10:19 uses the same pair. Using CURRENT_TIMESTAMP would silently change ownership.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use explicit scheduled intervals for incremental jobs whose compute can queue, retry, repair, or run late.

Practical example. An hourly payments aggregation starts seven minutes late on shared compute but must publish the same 09:00–10:00 business window.

How to decide. Prefer source offsets or watermarks when they define completeness better than time. For schedule-owned batches, use half-open boundaries and a durable run identity. Do not treat a default parameter as a security control.

Databricks: inject trigger time and overrideable job parameters

First-minute product recall: Day29 showed parameter precedence and Day46 preserved row position. Today the parameter itself becomes the interval contract.

# Lakeflow Jobs task parameters; not executed in productwindow_end = {{job.trigger.time.iso_datetime}}window_start = {{(job.trigger.time - 1.hours).iso_datetime}}run_id = {{job.run_id}}

Dynamic references are replaced with strings when the task runs. Cron trigger time is distinct from job start time. For repairs and backfills, expose explicit job parameters and persist the resolved values. Users with CAN MANAGE RUN or higher can override job parameters, so defaults are not authorization.

9 minutes · product implementation

Snowflake: read the current and last successful task-graph schedule

First-minute product recall: Day28 separated retry identity from one attempt. Runtime info now supplies stable graph boundaries across a retry group.

-- Snowflake SQL inside a task; not executed in productSELECT SYSTEM$TASK_RUNTIME_INFO(  'LAST_SUCCESSFUL_TASK_GRAPH_ORIGINAL_SCHEDULED_TIMESTAMP');SELECT SYSTEM$TASK_RUNTIME_INFO(  'CURRENT_TASK_GRAPH_ORIGINAL_SCHEDULED_TIMESTAMP');

The two values form a useful task-graph interval and stay consistent through the graph. The function fails outside a task run. An automatic or manual retry keeps the original scheduled timestamp for the graph run group.
