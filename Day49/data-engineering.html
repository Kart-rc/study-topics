Understand the idea · 4 min

A conference badge proves who entered the building. It does not open every room. Workload identity federation works the same way: an AWS role obtains a short-lived signed identity token, a platform policy matches the issuer, audience, and subject, and the platform maps that claim to a non-human identity.

That answers who is calling. SQL grants and platform privileges separately answer what the caller may do. A valid token with no SELECT grant must still be denied.

A worked example

An EKS service account assumes the AWS role orders-etl. The token says issuer = the account-specific AWS issuer, audience = databricks or the configured Snowflake audience, subject = that role. A matching federation rule authenticates the pipeline. The pipeline can read ops.orders because its platform identity has that grant; it cannot drop the catalog.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use workload identity federation when an unattended AWS workload must call a data platform and you want to remove long-lived platform secrets.

Practical example. An EKS-hosted Spark control service triggers a Databricks job and a Snowflake validation query using its AWS identity.

How to decide. Federate a stable, narrowly scoped workload identity when the runtime can mint verifiable short-lived tokens. Keep a managed secret only when the product, driver, or identity provider does not support federation, and rotate it explicitly.

9 minutes · product implementation

Databricks: map the AWS role to a service principal, then grant only the data path

Predict first. A matching AWS token can authenticate as a Databricks service principal; it still needs workspace and Unity Catalog privileges.

-- SQL grant sketch; not executed in DatabricksGRANT USE CATALOG ON CATALOG main TO `sp-orders-etl`;GRANT USE SCHEMA ON SCHEMA main.ops TO `sp-orders-etl`;GRANT SELECT ON TABLE main.ops.orders TO `sp-orders-etl`;

An account admin creates an account-level service-principal federation policy that matches the AWS issuer, audience, and role ARN. AWS grants sts:GetWebIdentityToken; the workload exchanges the short-lived token for Databricks OAuth. The current documentation recommends a short duration and allows at most 20 federation policies per service principal.

Execution label. SQL and CLI/API setup were not run in Databricks. This browser is a local JavaScript gate model; the Python replay is local.

9 minutes · product implementation

Snowflake: bind the AWS identity to a SERVICE user, then assign a least-privilege role

Predict first. The service user authenticates through WIF; the assigned Snowflake role supplies warehouse and object privileges.

-- sourced SQL sketch; not executed in SnowflakeCREATE USER orders_etl  WORKLOAD_IDENTITY=(TYPE=AWS ARN='arn:aws:iam::123:role/orders-etl'    ISSUER='https://issuer.tokens.sts.global.api.aws')  TYPE=SERVICE DEFAULT_ROLE=orders_etl_role;GRANT USAGE ON WAREHOUSE transform_wh TO ROLE orders_etl_role;GRANT SELECT ON TABLE ops.public.orders TO ROLE orders_etl_role;

For the current JWT-based AWS path, the Python connector requires version 4.7.1 or later and workload_identity_aws_use_outbound_token=True. Setting that option before the user has an ISSUER causes immediate authentication failure. The driver and SQL were not run here.

Execution label. SQL and connector calls were not run in Snowflake. The browser does not verify tokens or Snowflake RBAC.
