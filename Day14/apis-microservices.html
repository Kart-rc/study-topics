Understand the idea · 4 min

A waiter does not walk to the kitchen separately for every item on one table’s order. The waiter gathers the slips and makes one trip.

GraphQL field resolvers run independently. If three posts each resolve an author by calling the database, you can get one query for posts plus three author queries. That is the N+1 problem.

Posts query

1 database call

Three resolvers

u1, u2, u1

Request loader

batch [u1, u2] in 1 call

Naive: 4 calls · batched: 2 calls

A worked example

The response contains posts P1, P2, and P3. Their author IDs are u1, u2, and u1.

  1. Fetch the posts: one query.
  2. Each resolver calls loader.load(authorId).
  3. The loader collects keys for the same execution turn.
  4. It fetches unique authors u1 and u2 in one database call and returns results in key order.
userLoader = new DataLoader(ids => getUsersByIds(ids))
resolve(post, _, ctx) {
  return ctx.userLoader.load(post.authorId)
}

Create the loader per request. A long-lived cross-user cache can return stale data or leak information across authorization contexts.

What this code proves—and what it leaves out

Executes Python call-count arithmetic. It does not run GraphQL.js, DataLoader, a database, asynchronous scheduling, or authorization checks.

Optional deeper explanation and original worked example

Batching is not a license for unbounded IN queries. Cap batch size, keep authorization in the data access path, expose per-operation database-call metrics, and combine batching with GraphQL operation complexity controls.

What this model does and does not represent
The model counts logical database calls. It does not model SQL limits, batching windows, async scheduling, authorization, cache invalidation, errors per key, or the required result ordering in a real DataLoader batch function.
