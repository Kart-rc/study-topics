Understand the idea · 4 min

A warehouse expects boxes with three labels: order_id, amount, and event_time. One morning a box also has coupon_code. The safe question is not simply “Can the system add it?” It is “Should this load pause for review, preserve the unexpected field separately, or change the table automatically?”

Schema evolution is a policy decision at the ingestion boundary. The data can be preserved while the published contract remains controlled.

A worked example

File 1 has three columns. File 2 adds coupon_code=FALL10. A pause-and-restart path updates approved schema before File 2 continues. A rescue path keeps the current table columns and stores the extra field in a JSON rescue column. An automatic-evolution path adds a table column only when its required flags and privileges are present.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use an explicit schema-drift policy for semi-structured or partner files whose columns can change independently of your pipeline release.

Practical example. A retail partner adds coupon_code before your silver-table model is ready. Preserve the value, alert the owner, and expose it only after contract review.

How to decide. Pause and restart when every new column must be visible and reviewed. Rescue when continuity matters more than immediate promotion. Allow table evolution only for trusted file loads with naming, privilege, downstream-compatibility, and observability controls.

9 minutes · product implementation

Databricks: fail-and-restart or rescue deliberately

Mechanism. With Auto Loader and addNewColumns, discovery of a new column updates schema information and the stream initially fails; after restart it uses the evolved schema. With rescue, the schema does not evolve and unexpected fields land in _rescued_data.

# sourced PySpark; not executed here(spark.readStream.format("cloudFiles") .option("cloudFiles.format", "json") .option("cloudFiles.schemaLocation", schema_path) .option("cloudFiles.schemaEvolutionMode", "rescue") .load(source_path))

Failure/fix. addNewColumns without restart handling stops at the drift boundary. Configure Jobs retry/restart and alerting, or choose rescue when a stable landing schema is required.

Limits. Supplying a fixed schema changes supported modes; use schema hints for known types. Existing column types do not automatically evolve in the same way. This local model made no Databricks call.

9 minutes · product implementation

Snowflake: COPY evolves only when all gates are open

Mechanism. File-load schema evolution requires the table flag, MATCH_BY_COLUMN_NAME, and a loading role with EVOLVE SCHEMA or ownership. It applies to COPY INTO and Snowpipe file loads, not ordinary INSERT.

-- sourced SQL; not executed hereALTER TABLE raw_orders  SET ENABLE_SCHEMA_EVOLUTION = TRUE;COPY INTO raw_orders FROM @orders_stage  FILE_FORMAT = (TYPE = PARQUET)  MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;

Failure/fix. Missing any gate means the table does not evolve as intended. Provision the narrow privilege, enable the table deliberately, and test file-format rules.

Limits. Evolution can add columns and can drop NOT NULL from columns absent in new files. CSV has additional PARSE_HEADER/count-mismatch requirements. This local model made no Snowflake call.
