Understand the idea · 4 min

A scale can report that a package is overweight. It does not decide whether to label the package, remove one item, or stop the truck.

A data-quality rule has three parts: the condition, the measured result, and the consequence. Databricks Lakeflow expectations evaluate rows inside a pipeline and can warn, drop rows, or fail an update. Snowflake data metric functions run on a schedule and return measurements; expectations and notifications interpret those measurements. Monitoring alone does not rewrite or stop an unrelated load.

A worked example

A 100-row orders batch contains four rows with a missing order_id. Warn keeps 100 and records four failures. Drop publishes 96. Fail-update publishes no new version. A scheduled Snowflake NULL_COUNT can report 4; a separate expectation such as “value = 0” marks a quality issue and can notify.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use governed quality checks when a measurable defect has a named owner and a deliberate publication consequence.

Practical example. A bronze orders feed may retain and count malformed rows, while the finance-ready table must fail publication when any order ID is missing.

How to decide. Warn while learning a baseline, drop only when losing invalid rows is acceptable and auditable, fail when partial publication is unsafe, and notify when asynchronous monitoring is the right control. Do not turn every anomaly into a pipeline outage.

9 minutes · product implementation

Databricks: expectations sit inside the pipeline update

The rule travels with the transformation. Lakeflow expectations use SQL Boolean expressions on streaming tables, materialized views, or views. Default EXPECT retains invalid rows and records metrics. ON VIOLATION DROP ROW removes them. ON VIOLATION FAIL UPDATE fails the flow and atomically rolls back a table update.

-- sourced SQL sketch; not executedCONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL)  ON VIOLATION FAIL UPDATE

Failure/fix. In a triggered pipeline, one failed flow does not automatically fail independent parallel flows. Design the dependency/publication boundary explicitly. Metrics also have documented object/operator limits.

Execution label. SQL is an unexecuted vendor sketch. The row-flow view is local JavaScript.

9 minutes · product implementation

Snowflake: DMFs measure on a schedule; expectations interpret results

The monitor revisits the table. Associate a system or custom DMF with a table or view and set DATA_METRIC_SCHEDULE. The DMF returns a measurement such as null count, freshness, duplicates, or schema changes. An expectation defines which result is a problem; notifications can report violations. Data Quality Monitoring is documented as an Enterprise Edition feature.

-- sourced SQL sketch; not executedALTER TABLE PROD.ORDERS  ADD DATA METRIC FUNCTION SNOWFLAKE.CORE.NULL_COUNT  ON (ORDER_ID);

Failure/fix. A DMF result of four does not itself remove rows or undo the load. Bind an expectation, notification, and owner; add an orchestration gate separately when publication must stop.

Execution label. No Snowflake SQL ran. The scheduled measurement view is local JavaScript.
