Retry only the broken part of a workflow—and make every retried task safe to run again.

Understand the idea · 4 min

Picture a three-stop delivery route: ingest → validate → publish. Ingest finished. Validate wrote 60 rows, then failed. Publish never started. Repair should resume at validate, not repeat the successful ingest.

But repair is not magic rollback. The failed task usually starts again from its beginning. If it appends the same first 60 rows again, the table now contains duplicates. The scheduler chooses where to restart; task code decides whether restarting is safe.

A worked example

Run 17 ingests 100 orders. Validate writes orders 1–60 and crashes on order 61. A repair leaves ingest alone, restarts validate, and schedules publish only after validate succeeds. Safe validate uses MERGE on order_id or replaces the run partition. Unsafe validate blindly appends and turns 60 existing rows into 120.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use repair/retry after a multi-task workflow partially fails and successful upstream work is still valid.

Practical example. A nightly order workflow ingested its source once, but validation failed after a partial write and publishing was skipped.

How to decide. Repair the smallest failed branch only after checking every restarted task’s write pattern. Prefer MERGE, overwrite-by-run, or a processing marker; do not assume the orchestrator makes an append idempotent.

9 minutes · product implementation

Databricks: Repair run selects tasks; your code supplies idempotence

Use case. A Lakeflow Jobs run has successful ingest, failed validation, and dependent publish tasks.

Unexecuted example. The repair action reruns unsuccessful tasks; the task SQL must make a replay safe.

-- Inside the restarted validation taskMERGE INTO silver.orders AS tUSING staged_run_17 AS sON t.order_id = s.order_idWHEN MATCHED THEN UPDATE SET *WHEN NOT MATCHED THEN INSERT *;

Failure/fix. Databricks documents that repair reruns each unsuccessful task from the beginning and does not make tasks idempotent. Replace append with MERGE/overwrite when partial output can survive the failure.

9 minutes · product implementation

Snowflake: RETRY LAST starts at failed tasks in the task graph

Use case. The last graph run is FAILED or CANCELED and the graph definition is unchanged.

Unexecuted Snowflake SQL.

-- Retry the latest eligible failed graph runEXECUTE TASK order_pipeline RETRY LAST;-- Or target a known earlier graph-run groupEXECUTE TASK order_pipeline  RETRY GRAPH RUN GROUP 'group-id';

Failure/fix. RETRY LAST has eligibility rules: the last graph run failed/canceled, the graph is unchanged, and the first attempt is within 14 days. It creates a new attempt that begins at failed tasks. Query history and target a graph-run group when “latest” is not the run you mean.
