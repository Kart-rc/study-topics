## Required teaching style: plain language and visible examples

User feedback on 2026-09-29: the write-ups were difficult to understand. Senior-level depth must not depend on compressed language or unexplained jargon.

- Start with a concrete problem and a familiar example before naming the pattern. Give the learner a reason to care in one plain sentence.
- Carry one small example through the entire lesson: the same order, event, record, message ID, or numeric inputs in the explanation, diagram, interaction, and quiz. Show the actual before-and-after state.
- Use short sentences and short paragraphs. Introduce one idea at a time. Explain a technical term immediately in everyday language, then give its formal name. For example: “save both changes or save neither” before “atomic transaction”; “doing it again leaves the same result” before “idempotence.”
- Include at least one explanatory visual in every standalone lesson: an embedded SVG/HTML diagram, labeled timeline, or visible state comparison. Render the visual; do not make the learner interpret ASCII art or raw Mermaid text in an offline HTML page.
- Make each visual answer a question. Label actors and arrows with plain actions. Show which system remembers what, what changes at a step, and which changes survive failure. Keep text readable on mobile.
- For failure-oriented topics, show a successful run, the exact failure point, what persists, and what happens on retry. Explain both the broken approach and the fix using the same example.
- Make the interactive example show the mechanism through changing records, queues, ownership, or state—not only a slider that prints a formula. Start with a useful default and a short prediction prompt.
- Explain why the fix works, then state its precise limit in plain language. Avoid broad claims such as “exactly once” unless the protected effect and assumptions are explicit. Keep advanced caveats in a short optional deeper section.
- Use quizzes grounded in the example: “The app crashes here. What is saved? What happens next?” Explain wrong choices as well as the correct one.
- Keep the existing 15-minute budget inclusive of review. Favor a narrower topic taught clearly over more terminology. Preserve research accuracy, sources, original examples, and senior-level design judgment.
- From Day16 onward, include a visible **Use case: when to use this** section in every HTML lesson and its Markdown companion. Keep it within the existing four-minute explanation: state the real problem or signal that makes the idea relevant, give a concrete practical example, and explain how to decide whether to employ it or choose a simpler alternative. Prefer examples relevant to AWS/data platforms when natural. For research topics, distinguish specialist or potential uses from production-ready applications; do not invent a practical deployment. Keep optional depth outside the core reading path. Store the section in `lessons.json` as `use_case` with nonempty `when`, `example`, and `decision` fields; the renderer requires these for Day16 onward. Preserve prior quiz identities, recorded executions, source dates, and spaced-review history during editorial updates.
- Acceptance check: after reading once, the learner should be able to describe the problem, point to the failure in the visual, predict a retry, and explain the fix without repeating jargon.

Reference teaching example: for Kafka-to-database idempotent consumers, show an order's delivery row and its processed-message marker saved in the same database transaction. Prefer inserting the unique marker first and applying the business change only if insertion succeeds. Commit Kafka progress only after the database commits. Explain that the record can be read repeatedly while its database effect is applied once; external email/payment calls are outside that transaction. Use the next offset for the Kafka bookmark (e.g., resume at 43 after handling record 42 in a contiguous toy stream). Do not imply every SQLite uniqueness error automatically rolls back the entire transaction; an error-based implementation must explicitly roll back and distinguish the marker conflict from unrelated failures.
