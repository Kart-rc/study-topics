Understand the idea · 4 min

Symptom first: the orders dashboard shows five item rows, but the source manifest says the batch should contain three. Ingest is green and consumer lag is zero. Those signals prove movement, not correctness.

Treat the raw batch like a sealed evidence bag: stop publish, preserve the original input and checkpoint, repair into a new candidate, validate the counts, then promote it. Do not edit the visible gold table while still discovering the failure.

A worked example

Batch B22 contains four envelopes: valid o-41 with two items, a duplicate o-41, valid o-42 with one item, and malformed o-43. Naive flattening emits five rows. The repaired result is two orders and three item rows; one duplicate is excluded and one malformed envelope is quarantined.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this recovery sequence when a batch passed transport checks but violates a business invariant after parsing, deduplication, or flattening.

Practical example. A retail order batch is present and on time, yet repeated events and bad JSON inflate the gold item count.

How to decide. Contain first when visible data may be wrong. Replay from preserved raw data into an isolated candidate; publish only after explicit reconciliation. For a harmless late batch, normal retry may be enough.

After a Databricks Delta sink commit, restarting with the same valid checkpoint replays a batch. What protects the copied rows?

Recall first, then reveal the product refresher

Same query + batch in Delta. The same query/batch can be recognized by the Delta sink. A new query identity changes that boundary. This says nothing about independent duplicate business events.

You SELECT a Snowflake stream, then INSERT from it inside a transaction that rolls back. What persists?

Recall first, then reveal the product refresher

Neither change persists. SELECT does not consume the stream. The rolled-back consuming transaction preserves the old target and stream position, allowing a retry.

9 minutes · product implementation

Databricks: isolate, repair, validate, then let the job DAG publish

Use case. Replay preserved bronze records into a candidate table without changing the current gold table.

Prepared real lab. Use an authorized non-production workspace, Unity Catalog objects, and a job identity limited to read bronze, write the repair schema, and publish the approved target. Compute can incur cost.

The SQL below is unexecuted vendor code. Exact VARIANT availability and syntax depend on your supported Databricks Runtime.

CREATE OR REPLACE TEMP VIEW parsed AS
SELECT *, try_parse_json(payload) AS v FROM bronze.orders_b22;CREATE OR REPLACE TEMP VIEW deduped AS
SELECT * EXCEPT(rn) FROM (SELECT *, row_number() OVER (PARTITION BY event_id ORDER BY ingested_at) rn FROM parsed WHERE v IS NOT NULL) WHERE rn=1;CREATE OR REPLACE TABLE repair.b22_items AS
SELECT event_id, item.value FROM deduped, LATERAL variant_explode(v:items) item;-- Job task publish depends_on validate; run_if: ALL_SUCCESS

Failure/fix. Writing gold inside the parse step makes partial repair visible. Write an isolated candidate, have a separate validation task compare counts, and allow publish only after success. A job DAG does not replace table-level transactions or Unity Catalog privileges.

9 minutes · product implementation

Snowflake: quarantine parse failures, flatten the candidate, gate the task

Use case. Build the same evidence chain in a repair schema, then let a downstream task publish only the reconciled candidate.

Prepared real lab. Use an authorized non-production database, schema, warehouse, and task-owning role. Warehouse and task execution can incur credits.

The SQL is unexecuted vendor code.

CREATE OR REPLACE TEMP TABLE parsed AS
SELECT *, TRY_PARSE_JSON(payload) v FROM bronze.orders_b22;CREATE OR REPLACE TEMP TABLE deduped AS
SELECT * EXCLUDE rn FROM (SELECT *, ROW_NUMBER() OVER(PARTITION BY event_id ORDER BY ingested_at) rn FROM parsed WHERE v IS NOT NULL) QUALIFY rn=1;CREATE OR REPLACE TABLE repair.b22_items AS
SELECT event_id, f.value FROM deduped, LATERAL FLATTEN(INPUT => v:items) f;CREATE TASK publish AFTER validate AS CALL publish_b22();

Failure/fix. PARSE_JSON can abort on malformed input. TRY_PARSE_JSON exposes a NULL that you must quarantine and count; silently dropping it loses reconciliation evidence. Clustering is a separate, evidence-driven performance choice.
