Model a pipeline as a DAG where publish waits for validated data and cleanup still runs after failure.

Understand the idea · 4 min

A restaurant does not serve a plate before the safety check. A data workflow needs the same rule: publish depends on validation succeeding.

A directed acyclic graph, or DAG, records those prerequisites. It allows independent work to run together, but it prevents the final step from starting early.

A worked example

Batch B21 lands 1,000 rows. The quality task finds 12 invalid customer IDs. A correct graph blocks publish, records the failed gate, and still runs cleanup or notification.

The green “ingest succeeded” signal is not enough. The business outcome is whether only validated rows become visible.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use task dependencies when later work is unsafe or meaningless until named prerequisites finish.

Practical example. Ingest sales, validate keys, publish a gold table only after validation, and notify after the graph finishes.

How to decide. Use a DAG for durable, observable multi-step work. Keep one atomic SQL transaction when all changes fit one database and one short unit of work.

Recall first, then reveal the product refresher

No; metadata is automatic, while a key can improve layout for suitable large tables. Snowflake records micro-partition metadata automatically. User clustering keys are selective optimizations and are unsupported for hybrid tables.

Databricks: Lakeflow Jobs dependencies and Run if

Use case. Keep a gold-table publish task behind a data-quality task while a failure handler records bad batches.

Prepared real lab. Use an authorized non-production Databricks workspace and job identity with permissions to manage/run the job. Compute and task runs can incur cost.

Why this is not SQL first. This is job control, so the example uses declarative job YAML. The SQL belongs inside the tasks; there is no SQL statement in this lesson that creates the Lakeflow Jobs DAG.

The YAML is not applied in Databricks. Buttons replay a local state model.

- task_key: validate- task_key: publish
  depends_on: [{task_key: validate}]
  run_if: ALL_SUCCESS- task_key: notify_failure
  depends_on: [{task_key: validate}]
  run_if: AT_LEAST_ONE_FAILED

Failure/fix. ALL_SUCCESS blocks publish after validation failure. A separate failure task handles notification. Excluded/upstream-failed states have documented rules, so test the exact branch.

9 minutes · product implementation

Snowflake: CREATE TASK … AFTER and one finalizer

Use case. Express the same quality gate as a Snowflake task graph, using SQL DDL.

Prepared real lab. Use an authorized non-production database/schema, a task-owning role, and either serverless tasks or a warehouse. Ownership, warehouse usage, and task execution can incur cost.

The SQL is not run on Snowflake. Buttons replay a local state model.

CREATE TASK ingest SCHEDULE='USING CRON 0 * * * * UTC' AS CALL load_b21();CREATE TASK validate AFTER ingest AS CALL assert_b21_quality();
CREATE TASK publish AFTER validate AS CALL publish_b21();CREATE TASK finish FINALIZE = ingest AS CALL record_graph_result();

Failure/fix. A child with multiple parents waits for successful predecessors; a finalizer runs after other tasks finish or fail. Snowflake documents graph ownership, limits, resume steps, and retry behavior—DDL creation alone does not activate a production graph.
