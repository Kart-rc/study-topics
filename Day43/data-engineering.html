Understand the idea · 4 min

A restaurant can open on time only if five things line up: ingredients arrive, the cook finds the right items, spoiled food is rejected, the menu changes without disappearing, and enough tables are open.

A data product has the same chain. An arrival trigger starts work. Storage statistics skip irrelevant files or micro-partitions. A quality gate decides whether the candidate may continue. Atomic publication keeps the old table visible until the new one is ready. Query evidence decides whether to add clusters for waiting queries or size for one hungry query.

A worked example

At 8:52 AM, twenty payment files arrive. A date and tenant filter needs only three storage blocks. The candidate has 100 rows; four have a null account ID. The release must leave yesterday's table live. After correction, the candidate publishes as version 43. At 9:00 AM, thirty dashboard queries arrive; three ten-slot lanes clear the queue.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this release chain when a business dashboard or regulated data product has freshness, correctness, continuity, and query-latency obligations at the same time.

Practical example. A finance payments dashboard must be current by 9 AM, never expose invalid account rows, and remain queryable during publication.

How to decide. Treat each mechanism as a separate control with its own evidence. Do not use more compute to hide a quality failure, do not publish by dropping the live table, and do not assume an arrival trigger proves data was processed.

9 minutes · product implementation

Databricks: make a failed expectation leave the previous table live

Follow one candidate. A file-arrival trigger wakes a Lakeflow Job. The transform filters by date and account so Delta file statistics can skip irrelevant files. A pipeline expectation with ON VIOLATION FAIL UPDATE stops and atomically rolls back that update when an invalid row appears. Publish a validated full replacement with CREATE OR REPLACE TABLE; then inspect queue and spill evidence separately.

-- sourced SQL sketch; not executedCONSTRAINT valid_account EXPECT (account_id IS NOT NULL)  ON VIOLATION FAIL UPDATE;CREATE OR REPLACE TABLE finance.payments_live ASSELECT * FROM finance.payments_candidate;

Failure/fix. A failed expectation rolls back that update, but Databricks notes that parallel flows in a triggered pipeline do not all fail automatically. Put validation and publication in explicit task control flow when the whole release must stop.

Execution label. SQL and product triggers were not run. The state path is local JavaScript.

9 minutes · product implementation

Snowflake: measure quality, then make the swap an explicit release gate

Follow the same candidate with different mechanics. A stream can wake a triggered task. Micro-partition metadata prunes storage. A data metric function (DMF) measures quality and expectations can notify on thresholds, but that is not the Databricks fail-update transaction. Your orchestration must read the result and refuse publication. ALTER TABLE candidate SWAP WITH live performs the name swap only after that gate passes.

-- sourced SQL sketch; not executedALTER TABLE payments_candidate  ADD DATA METRIC FUNCTION SNOWFLAKE.CORE.NULL_COUNT ON (account_id)  EXPECTATION no_nulls (VALUE = 0);-- after orchestration verifies the result:ALTER TABLE payments_candidate SWAP WITH payments_live;

Failure/fix. An expectation that emits evidence is not itself a publication rollback. Wire the quality result into task control, then swap. Multi-cluster targets concurrent queued queries and consumes more credits; it does not repair bad data.
