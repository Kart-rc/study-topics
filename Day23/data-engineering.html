Understand the idea · 4 min

This is the fire-drill day. You are given a symptom, not a feature name. Your job is to choose the next control and explain what evidence would prove it worked.

The six prior lessons covered recovery, access paths, pruning, nested data, orchestration gates, and one combined repair. Retrieval matters because an exam or incident will not label the chapter for you.

A worked example

Orders batch B23 has four symptoms: a retry repeated output, an analyst cannot read the candidate, a date filter scans almost everything, and publish ran after validation failed. The correct response is not “optimize the pipeline.” Each symptom points to a different mechanism and a different proof.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use a retrieval-and-gap session after a run of focused lessons to test whether you can select controls from symptoms without feature-name prompts.

Practical example. Triage a failed orders pipeline by matching duplicate output, denied access, poor pruning, and unsafe publish to different remedies.

How to decide. Count an area as delivered when the lesson exists. Count it as retained only after a fresh private answer or real sandbox action; silence is not evidence of mastery or failure.

9 minutes · product implementation

Databricks retrieval: identify the next evidence-producing action

Use case. A Lakeflow job is green at ingest, but the gold result is wrong. Select the next evidence-producing action rather than naming random features.

Prepared real lab. Use an authorized non-production workspace, job identity, Unity Catalog objects, and a small synthetic batch. Compute can incur cost.

The SQL/YAML is unexecuted vendor practice.

SELECT try_parse_json(payload) AS v FROM bronze.b23;SELECT event_id, count(*) FROM bronze.b23 GROUP BY event_id HAVING count(*)>1;-- inspect job task: publish depends_on validate; run_if: ALL_SUCCESS-- then compare candidate counts before promotion

Failure/fix. A green ingest task is weak evidence. Query the failing invariant, preserve the source/checkpoint, repair in isolation, and test that the publish dependency blocks failure. This does not assess workspace navigation or hands-on speed.

9 minutes · product implementation

Snowflake retrieval: choose the query, privilege, or task evidence

Use case. The same B23 outcome can come from bad parsing, a missing privilege path, poor pruning, or an unsafe task graph. Retrieve the smallest diagnostic that separates them.

Prepared real lab. Use an authorized non-production database/schema, role, warehouse, and task graph. Warehouse and task execution can incur credits.

The SQL is unexecuted vendor practice.

SELECT TRY_PARSE_JSON(payload) v FROM bronze.b23;SHOW GRANTS TO ROLE b23_pipeline;SELECT * FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY()) ORDER BY start_time DESC;SELECT * FROM TABLE(INFORMATION_SCHEMA.COMPLETE_TASK_GRAPHS()) ORDER BY scheduled_time DESC;

Failure/fix. Granting broad ownership or increasing warehouse size can hide the symptom without proving the cause. Inspect the narrow path, then test both the intended success and denial/failure case.
