Understand the idea · 4 min

Imagine looking for page 42 in six labeled boxes. If every box says “pages 1–60,” you must open all six. If the labels are 1–10, 11–20, and so on, only one box can contain page 42. Data engines use the same idea: metadata records value ranges for a file or micro-partition, then a filter can skip chunks whose ranges cannot match.

This is pruning or data skipping. It reduces bytes considered by the scan. It does not create an index lookup, guarantee a duration, or fix a query that lacks a useful filter.

A worked example

Our synthetic orders table has 60 days across six equal chunks. The query is WHERE order_day = 42. A scattered layout gives every chunk a 1–60 range, so all six are candidates. A clustered layout gives non-overlapping ten-day ranges, so only the 41–50 chunk is scanned.

The browser model calculates candidates from the displayed ranges. It does not estimate cloud latency or cost. The product sections show how Databricks and Snowflake maintain related metadata but reorganize data through different mechanisms.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this when selective filters on a large table still scan many files or micro-partitions and query profiles show poor pruning.

Practical example. A daily sales table is repeatedly filtered by order_day for a narrow reporting window. The team compares scan candidates before and after changing physical layout.

How to decide. First confirm the predicate and scan profile. Reorganize only when repeated savings justify rewrite or maintenance cost; a small table or broad scan may not benefit.

After a Databricks Delta sink commit, restarting with the same valid checkpoint replays a batch. What protects the copied rows?

Recall first, then reveal the product refresher

Same query + batch in Delta. The same query/batch can be recognized by the Delta sink. A new query identity changes that boundary. This says nothing about independent duplicate business events.

You SELECT a Snowflake stream, then INSERT from it inside a transaction that rolls back. What persists?

Recall first, then reveal the product refresher

Neither change persists. SELECT does not consume the stream. The rolled-back consuming transaction preserves the old target and stream position, allowing a retry.

9 minutes · product implementation

Databricks: liquid clustering groups file ranges

Use case. A Unity Catalog managed Delta table is repeatedly filtered on order_day, and scan evidence shows overlapping file ranges.

Prepared real lab. Use an authorized non-production workspace, an existing unpartitioned Delta table study19.sales.orders with a top-level order_day, and a runtime that supports liquid clustering. OPTIMIZE ... FULL requires Databricks Runtime 16.4 LTS or above and can rewrite large amounts of data for hours. The operator needs privileges for ALTER/OPTIMIZE and compute; the reader needs SELECT. Compute and rewrite work can incur cost.

9-minute route. First minute: recall the Day17 checkpoint and Day18 grant questions below. Next two: predict file candidates. Next four: step through SQL and ranges. Final two: explain when rewrite cost loses.

The SQL is not run on Databricks. Buttons execute a local JavaScript model. Predictive optimization can manage OPTIMIZE for eligible Unity Catalog managed tables; if enabled, Databricks recommends disabling scheduled OPTIMIZE jobs.

ALTER TABLE study19.sales.orders CLUSTER BY (order_day);OPTIMIZE study19.sales.orders FULL;SELECT SUM(amount) FROM study19.sales.orders WHERE order_day = 42;

Boundary. Liquid clustering is incompatible with partitioning and ZORDER on the same table. Statistics availability, filter shape and newly written data affect skipping. FULL is an explicit expensive rewrite, not a daily reflex.

9 minutes · product implementation

Snowflake: micro-partition pruning after clustering maintenance

Use case. A very large standard Snowflake table has repeated selective order_day filters and high micro-partition overlap.

Prepared real lab. Use an authorized non-production account with a standard table and a role that can inspect clustering information and alter the table. An active warehouse executes queries. Defining a clustering key enables Automatic Clustering maintenance; it consumes serverless credits and convergence is not immediate. Hybrid tables do not support clustering keys.

9-minute route. First minute: recall the due product questions below. Next two: inspect overlap. Next four: define the key and observe the maintenance state. Final two: decide whether scan savings justify ongoing credits.

The SQL is not run on Snowflake. Buttons execute a local JavaScript model. The teaching ranges change immediately only to make the effect visible; real Automatic Clustering works asynchronously.

SELECT SYSTEM$CLUSTERING_INFORMATION('STUDY19.SALES.ORDERS', '(ORDER_DAY)');ALTER TABLE study19.sales.orders CLUSTER BY (order_day);SELECT SUM(amount) FROM study19.sales.orders WHERE order_day = 42;

Boundary. Snowflake already records micro-partition metadata automatically. A user clustering key is a targeted choice for large tables with suitable query patterns, not a prerequisite for pruning. Automatic maintenance costs credits and old results can remain cached separately from pruning.
