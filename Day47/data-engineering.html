Understand the idea · 4 min

A stadium has 10,000 ticket scans and one 20-row gate map. It is cheaper to give every scanner a copy of the tiny map than to send all ticket scans to one map.

A broadcast join copies a small relation to workers that hold partitions of the large relation. Each worker joins locally. This can remove a large shuffle, but the copied side must fit comfortably in worker memory.

A worked example

Four workers each hold 2.5 million payment rows. The merchant dimension has 5,000 rows and is 8 MB. Broadcasting sends 8 MB to each worker: 32 MB total. Shuffling both inputs would move the 10-million-row fact side as well. If the “small” side grows to 2 GB, four copies can turn the optimization into memory pressure.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use small-side join planning when a very large fact table repeatedly enriches from a genuinely small, reusable dimension.

Practical example. Ten million card events join to 5,000 merchant-risk records before an hourly fraud aggregate.

How to decide. First measure compressed and runtime size, freshness, skew, and the physical plan. Broadcast only when the copied side is safely small. On Snowflake, inspect the optimizer's chosen plan rather than looking for a Databricks-style broadcast hint.

9 minutes · product implementation

Databricks: hint the small alias, then verify the executed plan

Predict first. The hint names the exposed table alias on the small side.

-- sourced SQL sketch; not executed in DatabricksSELECT /*+ BROADCAST(m) */ p.payment_id, m.risk_bandFROM payments p JOIN merchant_risk mON p.merchant_id = m.merchant_id;

Databricks documents BROADCAST as the highest-priority join hint and says it can override the automatic broadcast threshold. A hint is still not guaranteed when the strategy does not support the join. AQE may adapt from runtime statistics; a pre-planned broadcast can avoid first shuffling both sides.

9 minutes · product implementation

Snowflake: inspect the managed plan; DIRECTED controls scan order, not broadcast

Predict first. Snowflake does not expose Databricks' BROADCAST hint. Its optimizer chooses distribution.

-- sourced SQL sketch; not executed in SnowflakeSELECT p.payment_id, m.risk_bandFROM payments p JOIN merchant_risk m  ON p.merchant_id = m.merchant_id;

Use Query Profile to inspect operator row counts, time, and data movement. Snowflake's DIRECTED syntax can constrain join/scan order; it is not a command to replicate a small table. Improve pruning, query shape, and warehouse fit only after plan evidence identifies the bottleneck.
