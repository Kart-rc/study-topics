Understand the idea · 4 min

A photocopy normally duplicates every page. A data clone can start more like two table-of-contents cards that point to the same sealed pages. Creating it is fast because the pages are not copied. When one side changes, new pages belong only to that side.

This is copy-on-write: share unchanged storage, separate changed storage. The important question is not only “Can I clone?” It is “Which files remain dependencies, which permissions copy, and what happens after the source changes?”

A worked example

Production has three immutable files: A, B, and C. A test clone initially reads all three. Test updates one order, so its new file D belongs only to test. Production still reads A+B+C. The clone reads the shared files plus D according to its own metadata. Storage grows for the changed portion, not for a second full copy.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use a clone to create a fast, isolated test or recovery starting point from an existing table. It fits short-lived QA, migration rehearsal, incident investigation, and controlled data repair.

Practical example. Create a test copy of a 10 TB orders table, change 2% of rows, validate a transformation, then discard the clone.

How to decide. Choose a sharing clone when speed and low initial storage matter and the source lifecycle is controlled. Choose a deep copy when the target must not depend on source files. Recheck grants, retention, external-table, stream, task, and object-type rules before production use.

9 minutes · product implementation

Databricks: choose SHALLOW or DEEP CLONE

Mechanism. A shallow clone copies table metadata and references source data files. A deep clone copies metadata and data files. After creation, source and target have independent metadata histories, but a shallow clone still needs readable source files.

-- sourced SQL; not executedCREATE TABLE qa.ordersSHALLOW CLONE prod.orders;CREATE TABLE archive.ordersDEEP CLONE prod.orders;

Failure/fix. A shallow clone can fail if source files are removed. Keep the source lifecycle compatible or use a deep clone when independence is required.

Limits. Runtime, catalog, source type, streaming table, materialized view, history, and privilege rules vary. The SQL above did not run.

9 minutes · product implementation

Snowflake: zero-copy clone, then copy-on-write

Mechanism. CREATE … CLONE creates a new object whose tables initially share existing micro-partitions. Each table has its own lifecycle. DML creates new micro-partitions owned by the table that changed.

-- sourced SQL; not executedCREATE SCHEMA qa CLONE prod;UPDATE qa.ordersSET status = 'REVIEW'WHERE order_id = 42;

Failure/fix. Cloning a database or schema does not mean every dependent object behaves identically. Review privileges, COPY GRANTS, tasks, streams, external objects, policies, and object-specific clone rules.

Limits. This local percentage model is not Snowflake storage accounting. SQL above did not run.
