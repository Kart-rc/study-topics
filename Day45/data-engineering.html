Understand the idea · 4 min

A warehouse receives four cartons. Two are correct, one has the right items under unfamiliar labels, and one is crushed. Throwing away the whole truck protects consistency but delays every good carton. Accepting everything without labels hides the damage.

Data ingestion needs the same explicit lanes: accepted rows, recoverable surprises, and records that could not be parsed. The useful control is not “ignore errors.” It is “keep every outcome countable and inspectable, then decide what may advance.”

A worked example

A payments file contains four rows: P-1 is valid; P-2 has amount="twelve"; P-3 is malformed JSON; P-4 is valid. The production decision is whether P-1 and P-4 may enter bronze while P-2 and P-3 remain visible for repair. The answer depends on downstream risk, reconciliation, and whether partial loading changes business meaning.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use explicit exception lanes when source files can contain recoverable drift or isolated corruption and delaying every valid row is more harmful than bounded partial progress.

Practical example. A partner sends hourly payment events; two valid records should remain available while a type mismatch and a truncated JSON record are investigated.

How to decide. Abort the batch when completeness is the contract or partial progress breaks reconciliation. Otherwise load valid rows only when rejected and rescued counts, source locations, alert thresholds, replay ownership, and publication gates are all explicit.

9 minutes · product implementation

Databricks: preserve drift in _rescued_data and malformed input in _corrupt_record

Predict first. P-2 has amount="twelve"; P-3 is truncated JSON. Which column should explain each?

# sourced PySpark sketch; not executed in Databricksdf = (spark.readStream.format("cloudFiles") .option("cloudFiles.format", "json") .option("cloudFiles.schemaHints", "_corrupt_record string") .option("columnNameOfCorruptRecord", "_corrupt_record") .load(source))

_rescued_data preserves fields missing from the schema or carrying type/case mismatches. _corrupt_record captures rows the parser cannot form. Databricks recommends the corrupt-record column over badRecordsPath because the latter can have race conditions. Monitor both columns and keep publication policy separate.

9 minutes · product implementation

Snowflake: preflight COPY errors, then choose abort or partial load deliberately

Predict first. What changes in the target when VALIDATION_MODE is used? Nothing: it tests files and returns errors instead of loading.

-- sourced SQL sketch; not executed in SnowflakeCOPY INTO payments FROM @landing/payments FILE_FORMAT=(FORMAT_NAME='payments_json') VALIDATION_MODE=RETURN_ERRORS;-- only after reviewing policy:COPY INTO payments FROM @landing/payments FILE_FORMAT=(FORMAT_NAME='payments_json') ON_ERROR=CONTINUE;

ON_ERROR=CONTINUE loads valid rows and reports errors; the rejected row is not stored in the target as a rescued-data column. Use COPY results and VALIDATE where supported. VALIDATE has limits, including no results for the default ABORT_STATEMENT and failure for COPY transformations.

Execution label. No Snowflake SQL ran; this is a local model of the documented policy.
