Understand the idea · 4 min

A passport office does not erase your old passport when it issues a new one. It stamps the old validity period closed and opens a new period.

A slowly changing dimension Type 2 table does the same for business facts. Each key has dated versions. A change for customer c56 at time 20 closes the current basic row at 20 and inserts pro starting at 20. The hard invariant is not “keep two rows”; it is “for one key, validity ranges do not overlap and one row is current.” Sequence evidence, duplicate handling, deletes, null rules, and late events must be explicit.

A worked example

Before: c56 | basic | [0,∞). After the event (c56, pro, ts=20): basic | [0,20) and pro | [20,∞). Replaying the exact event must not create a second pro row.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use Type-2 history when analytics or audit questions need the value that was valid at an earlier business time.

Practical example. A financial data platform must explain which customer tier and risk segment applied when an order was approved.

How to decide. Choose Type 2 only for attributes whose history matters. Use Type 1 for corrections where old values have no business meaning. Define sequence, tie, delete, late-arrival, and replay rules before choosing a product mechanism.

9 minutes · product implementation

Databricks: declare keys, sequence, and SCD Type 2 in AUTO CDC

First-minute product recall: Recall Day31: a change feed is evidence, not yet a correct history table.

-- Lakeflow Declarative Pipelines SQL; not executedCREATE OR REFRESH STREAMING TABLE dim_customer;CREATE FLOW customer_history AS AUTO CDC INTO dim_customerFROM STREAM(customer_changes)KEYS (customer_id)SEQUENCE BY event_tsCOLUMNS * EXCEPT (op, event_ts)STORED AS SCD TYPE 2;

AUTO CDC is Databricks’ recommended declarative path for CDC. It handles ordering and Type-2 history from a change feed, but you must still define keys, sequence, ignored columns, and delete semantics. Product/runtime prerequisites apply; inspect the generated target and late-event behavior rather than treating the clause as magic.

9 minutes · product implementation

Snowflake: make close-and-insert an explicit stream/task transaction

First-minute product recall: Recall Day31: a Snowflake stream exposes a change interval and advances when committed DML consumes it.

-- Snowflake SQL sketch; not executedBEGIN;UPDATE dim_customer d SET valid_to=s.event_ts, is_current=FALSE  FROM customer_stream s  WHERE d.customer_id=s.customer_id AND d.is_current;INSERT INTO dim_customer  SELECT customer_id,tier,event_ts,NULL,TRUE FROM customer_stream;COMMIT;

A stream plus triggered task can drive explicit change processing. Snowflake MERGE is useful, but Type 2 needs both closing the old row and inserting a new row; many designs stage action rows or use a stored procedure/explicit transaction. Deduplicate the source first because multiple source rows matching one target can make MERGE nondeterministic. This is not a direct managed equivalent of AUTO CDC.

Execution label. SQL was not run in Snowflake; this is a local JavaScript teaching model.
