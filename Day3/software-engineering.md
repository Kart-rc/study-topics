# Fencing tokens: stop the worker whose lease already died

Software engineering · Day3 · 15 minutes

Worker A pauses for a long time.

## Recall (2 minutes)

<p><a href="../Day2/software-engineering.html">Day2: A queue buys time, not capacity</a></p><p>Backlog 300, arrivals 80/s, service 100/s. Ideal drain time?</p><details><summary>Recall first, then reveal the refresher</summary><p>15 seconds. The drain rate is spare capacity: 100 − 80 = 20/s. 300 / 20 = 15 seconds.</p></details>

## Understand (4 minutes)

Worker A pauses for a long time. Its lease expires, so worker B takes over. When A wakes up, it still has a write ready. A lease alone cannot stop that old write.

A fencing token is a number that increases when a new owner is granted access. The storage boundary remembers the newest accepted token and rejects older ones. The resource performing the write must enforce the rule; an expired worker may not know it lost ownership.

Watch the visual: Where is a stale worker’s write actually stopped?



A has token 1. B has token 2 and saves a corrected snapshot. A’s late token-1 write is rejected, leaving B’s value intact.



## Read the visual

A lease ledger and the storage boundary remember different facts. A may retain token 1 after its lease expires. Once B writes with token 2, storage remembers 2. A’s delayed token-1 write is rejected at storage when fencing is enabled; disabling fencing lets stale data replace B’s value.


## Step through the code (within the 5-minute exploration)

Spend about two minutes here and three in the interactive lab. These are actual recorded executions of the synthetic example, replayed in the HTML page.

```java
int tokenA = 1;
int tokenB = 2;
int newestAccepted = tokenB;
String snapshot = "B corrected";
boolean allowA = tokenA >= newestAccepted;
snapshot = allowA ? "A stale" : snapshot;
```

1. A holds an earlier lease generation.

   Changed values: `{"tokenA": "1"}`

2. B receives a newer generation.

   Changed values: `{"tokenB": "2"}`

3. The resource records B’s accepted token.

   Changed values: `{"newestAccepted": "2"}`

4. B’s value is now stored.

   Changed values: `{"snapshot": "B corrected"}`

5. The resource rejects A’s stale token.

   Changed values: `{"allowA": "false"}`

6. Rejected work leaves the stored value unchanged.

   Changed values: `{}`

<p>A lease answers “who may act now?” only while every participant observes time and communication promptly. Every protected write carries the token. The resource remembers the greatest accepted token and rejects lower ones. Chubby’s original paper describes sequencers that clients can pass to servers so stale lock holders can be detected. ## Explore (remaining exploration time)

Run A → expire → B → B writes → A resumes with fencing on. Reset and repeat with fencing off. Predict the final value before each delayed write, then name the component that must store maxAccepted durably.

Open software-engineering.html for the executable model.

Model limits: A single in-memory resource, sequential button presses, one lease namespace, and perfect monotonically increasing grants. It omits quorum failure, lease renewal, token durability, retry idempotency, multi-resource transactions, storage APIs that cannot conditionally compare tokens, and recovery after the resource loses maxAccepted. Real designs must bind tokens to the correct resource and command.

## Quiz (4 minutes)

1. A has token 1, B's token-2 write was accepted, then A resumes. What should the resource do?
   - Accept A because it once owned the lease
   - Reject token 1 as stale
   - Ask A's wall clock

2. Why is a lock service alone insufficient in this race?
   - It cannot stop a paused former holder from later sending a delayed request
   - It never grants exclusive ownership
   - It always uses wall clocks

3. A storage API cannot atomically compare and record a fencing token. What is the boundary?
   - The token still guarantees safety by itself
   - An enforcing metadata or write path is required; otherwise the stale-write gap remains
   - Use a random token

4. Explain one design decision to a skeptical engineer.
5. Change one assumption. What breaks, and how would you detect it?

<details><summary>Answer key — attempt first</summary>

1. Reject token 1 as stale. The resource has already accepted token 2, so token 1 cannot be current.

2. It cannot stop a paused former holder from later sending a delayed request. The stale process still exists; the protected resource must recognize an obsolete grant.

3. An enforcing metadata or write path is required; otherwise the stale-write gap remains. A token is evidence, not enforcement. Some authoritative component must reject old tokens atomically.
