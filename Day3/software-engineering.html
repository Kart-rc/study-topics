Fencing tokens: stop the worker whose lease already died

Trace the stale-worker race and explain why lease ownership must be enforced at the resource, not trusted in the client.

Foundation · distributed coordination

Start with retrieval · 2 min

Day2: A queue buys time, not capacity

Backlog 300, arrivals 80/s, service 100/s. Ideal drain time?

Recall first, then reveal the refresher

15 seconds. The drain rate is spare capacity: 100 − 80 = 20/s. 300 / 20 = 15 seconds.

Build the mental model · 4 min

A lease answers “who may act now?” only while every participant observes time and communication promptly. A worker can pause after acquiring the lease, miss its expiry, and resume after a replacement has begun. Mutual exclusion at the lock service did not erase the paused process or its delayed request.

A fencing token is a monotonically increasing number issued with each ownership grant. Every protected write carries the token. The resource remembers the greatest accepted token and rejects lower ones. Chubby’s original paper describes sequencers that clients can pass to servers so stale lock holders can be detected. The enduring design lesson is that the resource must participate in enforcement.

A worked example

Original teaching case: Compactor A gets token 1 and pauses during a long runtime stall. Its lease expires. Compactor B gets token 2 and publishes a corrected snapshot. A resumes with a buffered token-1 write.

If the object-store publishing layer accepts “whoever writes last,” A can replace the newer snapshot. If a small authoritative metadata resource conditionally accepts only tokens at least as new as its recorded token, A is rejected. The lease service and resource therefore share a protocol:

grant → monotonically increasing token
write(resource, token, value)
resource accepts only token ≥ maxAccepted

Do not confuse the token with a timestamp generated by workers. A clock value need not be globally monotonic. Also decide the granularity: a token for one dataset must not accidentally fence unrelated datasets.

Explore · 5 min

Predict, change, explain

Run A → expire → B → B writes → A resumes with fencing on. Reset and repeat with fencing off. Predict the final value before each delayed write, then name the component that must store maxAccepted durably.

What this model does and does not represent
A single in-memory resource, sequential button presses, one lease namespace, and perfect monotonically increasing grants. It omits quorum failure, lease renewal, token durability, retry idempotency, multi-resource transactions, storage APIs that cannot conditionally compare tokens, and recovery after the resource loses maxAccepted. Real designs must bind tokens to the correct resource and command.
