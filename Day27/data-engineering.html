Make MERGE deterministic by reducing duplicate source events to one winner for each business key.

Understand the idea · 4 min

Think of a race with one podium place. If two runners both arrive for “order 42,” the referee must choose one winner before updating the official record. A database MERGE has the same need: each target row should see one source winner.

The safe shape is raw events → rank within each business key → keep rank 1 → MERGE. “Latest” needs a complete, deterministic order: event time plus an ingestion sequence or event ID for ties.

A worked example

Order 42 arrives twice: PACKED at 10:02, sequence 7 and SHIPPED at 10:05, sequence 9. Rank by event_time DESC, ingest_sequence DESC. SHIPPED becomes row 1. The MERGE sees only that row, so the target moves from PACKED to SHIPPED once.

A second order can be processed in the same batch because ranking is partitioned by order_id.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this before an upsert whenever one micro-batch or staged load may contain two records for the same target key.

Practical example. A Kafka retry and a late shipment event both put order 42 into the same landing batch.

How to decide. Define the business key, the winning order, and the tie-breaker explicitly. Reject or quarantine rows when the system cannot select a truthful winner.

9 minutes · product implementation

Databricks: rank the Delta source, then MERGE one row per key

Use case. Bronze contains retries and late order events. Silver must expose one current row per order.

Unexecuted Databricks SQL. The browser below is a local model; run SQL only in an authorized workspace.

WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (  PARTITION BY order_id  ORDER BY event_time DESC, ingest_sequence DESC ) AS rn FROM bronze.order_events)MERGE INTO silver.orders tUSING (SELECT * FROM ranked WHERE rn = 1) sON t.order_id = s.order_idWHEN MATCHED THEN UPDATE SET status = s.statusWHEN NOT MATCHED THEN INSERT *;

Failure/fix. Delta MERGE can reject ambiguous multiple source matches. Databricks also documents runtime-dependent duplicate-match evaluation. Do not encode correctness in that version difference: preprocess the source to one row per key.

9 minutes · product implementation

Snowflake: QUALIFY the staged source before MERGE

Use case. A staged Snowpipe or batch load contains more than one status row for an order.

Unexecuted Snowflake SQL. The browser is a local model; run SQL only with the intended role, warehouse, and change controls.

MERGE INTO curated.orders tUSING ( SELECT * FROM raw.order_events QUALIFY ROW_NUMBER() OVER (  PARTITION BY order_id  ORDER BY event_time DESC, ingest_sequence DESC ) = 1) s ON t.order_id = s.order_idWHEN MATCHED THEN UPDATE SET status = s.statusWHEN NOT MATCHED THEN INSERT (order_id,status) VALUES (s.order_id,s.status);

Failure/fix. With multiple conflicting source matches, Snowflake documents an error when the parameter is TRUE; FALSE may choose a value nondeterministically. Filtering to one source winner makes the result deterministic instead of weakening the guardrail. Duplicate unmatched source rows can also produce duplicate inserts, so dedupe before both paths.
