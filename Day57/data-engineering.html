Understand the idea · 4 min

A bakery misses the 9:00 delivery. The safe response is not “take every delivery now in the yard.” It is “replay the 9:00–10:00 manifest, count every box, then open the shop shelf.”

Our customer pipeline missed its 09:00–10:00 window. Customer c57 changed from basic to pro at 09:20. A sound recovery carries one fixed window through five controls: select only that interval, apply the Type-2 change once, verify one current row, retain a useful query layout, and publish only after the checks pass. Scheduling, history, performance, sharing, and deployment are one evidence chain—not five independent demos.

A worked example

Before recovery, c57 | basic | [08:00,∞). The replay reads only [09:00,10:00), closes basic at 09:20, and opens pro. Replaying the same event keeps two historical rows and exactly one current row. Only then does the provider expose the verified object.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this recovery pattern when a scheduled data interval was missed but its source history is still available and consumers need auditable publication.

Practical example. An enterprise customer dimension misses one hourly CDC run before downstream risk and reporting teams read it through a governed share.

How to decide. Freeze the business interval first. Prove source completeness, deterministic keys/order, one-current-row history, consumer query evidence, and publication state. If the source interval is no longer recoverable, stop and use a separately approved reconciliation or snapshot path.

9 minutes · product implementation

Databricks: carry one run window into AUTO CDC, validation, and sharing

First-minute product recall: Recall Day52’s trigger-owned interval and Day56’s ordered Type-2 change.

-- Databricks SQL sketch; not executedCREATE OR REFRESH STREAMING TABLE customer_dim  CLUSTER BY AUTO;AUTO CDC INTO customer_dim  FROM STREAM(customer_cdc_window)  KEYS (customer_id)  SEQUENCE BY event_ts  STORED AS SCD TYPE 2;

Pass window_start and window_end as job or pipeline parameters; scheduled jobs can derive stable trigger-time values. AUTO CDC owns ordered Type-2 mechanics, while a separate validation task proves source count and one current row before a share update or promotion step. CLUSTER BY AUTO is a workload-aware layout aid, not a correctness gate. AUTO CDC requires serverless Lakeflow pipelines or Pro/Advanced editions.

9 minutes · product implementation

Snowflake: stage the recovery set, transact history, inspect task evidence, then share

First-minute product recall: Recall Day52’s scheduled-time evidence and Day56’s atomic close-and-insert.

-- Snowflake SQL sketch; not executedBEGIN;UPDATE dim_customer d SET valid_to=s.event_ts,is_current=FALSE FROM recovery_0900 s WHERE d.customer_id=s.customer_id AND d.is_current;INSERT INTO dim_customer SELECT customer_id,tier,event_ts,NULL,TRUE FROM recovery_0900;COMMIT;

Materialize or otherwise identify the fixed recovery set before consuming it. Keep close-and-insert atomic and deduplicate staged changes. Use TASK_HISTORY evidence such as scheduled, query-start, completion, state, and graph version to prove which run occurred. Large secure-view workloads may justify clustering on the base table. Add the verified secure view to a share only after checks pass. This is an explicit pipeline; Snowflake has no direct managed AUTO CDC equivalent.
