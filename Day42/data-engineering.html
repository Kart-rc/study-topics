Add clusters for waiting queries; add size for a hungry query

Understand the idea · 4 min

A grocery store has two different problems. A long checkout line needs more open lanes. One oversized cart needs a lane with more room and staff.

SQL warehouses have the same split. Scale out adds clusters so more independent queries run at once. Scale up gives each cluster more compute and memory, which can help a single query that spills or scans heavily. More clusters do not automatically make one slow query fast.

A worked example

Thirty queries arrive together. One cluster can actively serve ten in the teaching model, so twenty wait. Three same-sized clusters can serve all thirty concurrently. But one query that needs 18 GB while a cluster offers 12 GB still spills; it needs a larger size or a better plan, not another identical cluster.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this distinction when dashboard or BI users report queues, when a query profile reports spill, or when cost rises after indiscriminate warehouse resizing.

Practical example. A finance dashboard opens at 9 AM with 30 short queries while one month-end aggregation spills to disk.

How to decide. Add concurrency capacity when many short queries wait. Increase size or optimize SQL when one query lacks memory or compute. Separate workloads when their SLOs and cost controls differ; measure queue and spill evidence before changing either knob.

9 minutes · product implementation

Databricks: use queue and spill evidence to choose the knob

Serverless manages admission and clusters for you. Intelligent Workload Management predicts requirements, queues work when capacity is unavailable, and scales clusters as waits grow. Cluster size remains the per-cluster resource choice. For classic and pro warehouses, you configure minimum and maximum clusters.

// sourced REST payload sketch; not executed{"name":"finance-bi", "cluster_size":"Medium", "min_num_clusters":1, "max_num_clusters":3}

There is no SQL CREATE WAREHOUSE equivalent here; use the UI, SQL Warehouses API, or Terraform with the required workspace privileges.

Failure/fix. A persistent Peak Queued Queries value above zero can justify more clusters; bytes spilled in Query Profile points toward size or query work. Warm-up and serverless behavior are not represented locally.

9 minutes · product implementation

Snowflake: multi-cluster is a concurrency control, not a slow-query cure

A multi-cluster warehouse adds same-sized compute clusters as queries queue. Auto-scale mode uses different minimum and maximum counts. STANDARD favors responsiveness; ECONOMY waits for enough load to keep another cluster busy. Multi-cluster warehouses require Enterprise Edition or higher.

-- sourced SQL sketch; not executedCREATE WAREHOUSE finance_bi WAREHOUSE_SIZE='MEDIUM' MIN_CLUSTER_COUNT=1 MAX_CLUSTER_COUNT=3 SCALING_POLICY='STANDARD' AUTO_SUSPEND=300;

Failure/fix. Snowflake explicitly says multi-cluster is best for concurrency. Resize the warehouse for a slow query or load when per-query resources are the constraint. More running clusters also consume more credits.
