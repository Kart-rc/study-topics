Understand the idea · 4 min

A carrier sends shipments.csv. At 09:00 it contains 100 orders. At 09:10 the carrier replaces the same path with a corrected file. The new batch has two rows for order 42. Validation then fails after writing 60 rows. Ten analysts are waiting, and a partner reads a live share.

This is not five separate problems. It is one release decision. A safe path must identify the corrected file, choose one winner for order 42, repair without duplicating rows, match compute to the workload, and expose only a certified view.

A worked example

The release has five gates. Identity: treat the corrected object as a new version, not “the same filename.” Winner: rank order 42 by event_time and a stable tie-breaker before MERGE. Repair: restart the failed branch with repeat-safe writes. Capacity: one heavy reconciliation query needs more per-query power; many waiting readers need concurrency. Share: add or keep the certified view only after reconciliation passes; revoke access if bad data escaped.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this runbook when a file-fed pipeline must recover from corrected inputs and publish current data to internal or external consumers.

Practical example. A logistics partner overwrites shipments.csv, duplicate business keys appear, validation partially writes, and a partner share is already live.

How to decide. Stop publication first. Prove input identity and one-row-per-key determinism, repair with idempotent writes, choose compute from queue/profile evidence, then expose the narrow certified object. Treat every gate as evidence, not a checkbox.

9 minutes · product implementation

Databricks: corrected object → ranked Delta source → repaired job → Delta Share

Use case. Auto Loader ingests partner objects; a Lakeflow Job ranks and merges them; Databricks SQL reconciles; Delta Sharing serves a certified view.

Unexecuted SQL/Python.

# New object versions need an explicit policy.option("cloudFiles.allowOverwrites", "true")-- One source winner per order before MERGEWITH ranked AS ( SELECT *, ROW_NUMBER() OVER (  PARTITION BY order_id ORDER BY event_time DESC, ingest_id DESC) rn FROM bronze_shipments)MERGE INTO silver_shipments tUSING (SELECT * FROM ranked WHERE rn=1) sON t.order_id=s.order_id ...;

Failure/fix. Auto Loader overwrite handling has caveats; make the object version/content key auditable. Repair reruns failed tasks from the beginning, so MERGE or replace-by-run must be repeat-safe. Size up for one query only after profiling; increase maximum clusters for concurrency. Grant the recipient only the share containing the certified object, and revoke it during containment if needed.

9 minutes · product implementation

Snowflake: content metadata → QUALIFY → MERGE → task retry → secure share

Use case. COPY/Snowpipe loads staged objects, a task graph curates them, a warehouse reconciles, and a Secure Share exposes a certified view.

Unexecuted Snowflake SQL.

COPY INTO landing_shipmentsFROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_CONTENT_KEY, METADATA$FILE_LAST_MODIFIED FROM @partner_stage);MERGE INTO silver_shipments t USING ( SELECT * FROM landing_shipments QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id  ORDER BY event_time DESC, file_content_key DESC)=1) s ON t.order_id=s.order_id ...;

Failure/fix. COPY load metadata helps avoid reloading files but has a 64-day boundary; retain business audit identity and do not rely on filename alone. A larger warehouse helps a heavy query; a multi-cluster warehouse targets concurrency and requires Enterprise Edition. Secure Sharing exposes current provider data, and access can be revoked.
