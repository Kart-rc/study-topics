Understand the idea · 4 min

A grocery shelf should switch from yesterday's price list to today's complete list in one move. Taking the old list down and building the new one line by line leaves shoppers with an empty or half-built list.

An atomic replacement makes one catalog decision: readers see the old complete table or the new complete table, never the gap between DROP and CREATE. Databricks replaces the contents while keeping the table identity and Delta history. Snowflake can swap the names of two prepared table objects in one transaction. Those are related outcomes, not the same mechanism.

A worked example

prod.orders has 3 validated rows. A rebuild creates 4 corrected rows. With drop-then-create, a reader between statements sees “table missing.” With Databricks CREATE OR REPLACE TABLE, the named table moves from version 7 to version 8. With Snowflake ALTER TABLE prod.orders SWAP WITH prod.orders_next, the two table names exchange objects atomically.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use atomic replacement when a full snapshot or corrected rebuild must become visible to concurrent readers as one publication event.

Practical example. A nightly customer dimension rebuild must publish 40 million validated rows without exposing an empty table to dashboards.

How to decide. Use incremental MERGE when only a small known delta changes. Use replacement when the entire result is authoritative, validation happens before publication, rollback is planned, and product-specific grants, policies, streams, dependencies, and history have been checked.

9 minutes · product implementation

Databricks: replace contents, keep the table identity

The same shelf gets a new complete edition. For Delta tables, CREATE OR REPLACE TABLE is one transaction. Databricks documents that the table identity and history remain, concurrent readers can continue, granted privileges are preserved, and matching column masks remain. A drop followed by create does not have those semantics.

-- sourced SQL sketch; not executedCREATE OR REPLACE TABLE prod.orders ASSELECT * FROM stage.orders_validated;-- rollback evidence: DESCRIBE HISTORY prod.orders;

Failure/fix. Drop/recreate breaks the active name-to-history link and can surprise concurrent work. Prefer replace for a supported Delta replacement, but verify schema, masks, row filters, dependencies, protocol/runtime constraints, and concurrent-write behavior.

9 minutes · product implementation

Snowflake: prepare blue and green objects, then swap their names

Two carts exchange shelf labels. Build and validate ORDERS_NEXT. ALTER TABLE ORDERS SWAP WITH ORDERS_NEXT renames the two table objects in one transaction. Afterward, the production name points to the prepared object and the previous production object remains under the other name for inspection or rollback.

-- sourced SQL sketch; not executedCREATE TABLE PROD.ORDERS_NEXT CLONE PROD.ORDERS;-- rebuild and validate ORDERS_NEXTALTER TABLE PROD.ORDERS SWAP WITH PROD.ORDERS_NEXT;

Failure/fix. A swap needs ownership on both tables plus the documented schema privilege, and temporary/permanent combinations have restrictions. Names move between objects; inspect grants, policies, streams, dependencies, retention, and rollback behavior rather than assuming Databricks-style identity preservation.
