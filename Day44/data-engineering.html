Understand the idea · 4 min

A parcel tracker can say “label created” even though the carrier never received the box. One green checkpoint does not prove the whole trip.

A data release has four separate claims: the trigger woke the graph, transformation produced the right candidate, publication changed the live version, and serving capacity met demand. Retrieval practice means naming which claim lacks evidence before choosing a repair. A gap is recorded as “not yet demonstrated,” never guessed from silence.

A worked example

A payments file arrives at 8:52. The graph starts, but the transform fails. The dashboard still reads version 43 from yesterday. The correct first statement is not “the trigger is broken” or “add a cluster.” It is “transform success is unproven.” After the cause is fixed, rerun the failed work and its dependent publication, then check the live version and query queue.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use a retrieval/gap session after several related lessons or before a certification practice set, especially when many controls can produce similar symptoms.

Practical example. A morning data product is stale even though an arrival trigger fired; the team must distinguish trigger, transform, quality, publication, and serving evidence.

How to decide. Start at the first unproven boundary and request its native evidence. Repair from there. Do not infer personal mastery from lesson delivery; only an explicit answer or real sandbox result can close a learner gap.

Databricks retrieval: inspect the failed task, then repair current code deliberately

Retrieve before revealing. A file-arrival run shows transform_payments failed and publish_live did not run. Name the smallest safe repair before reading on.

# sourced REST shape; not executedPOST /api/2.2/jobs/runs/repair{"run_id": 8044, "rerun_all_failed_tasks": true, "rerun_dependent_tasks": true}

A repair stays in the original run history, but unsuccessful tasks run with the current job and task settings. That is useful after a fix and dangerous if the definition drifted unintentionally. There is no SQL repair statement equivalent; this mechanism is a Jobs API/UI operation.

9 minutes · product implementation

Snowflake retrieval: use graph history to find the first error before RETRY LAST

Retrieve before revealing. A triggered task graph ended FAILED. The graph summary names the first error task; TASK_HISTORY supplies task-level error details and query IDs. Only then consider retry.

-- sourced SQL sketch; not executedSELECT state, first_error_task_name, first_error_messageFROM TABLE(INFORMATION_SCHEMA.COMPLETE_TASK_GRAPHS(  ROOT_TASK_NAME => 'PAYMENTS_ROOT'));-- after fixing the cause:EXECUTE TASK PAYMENTS_ROOT RETRY LAST;

RETRY LAST creates a new graph run beginning at failed tasks. It is not a rewind of external side effects, and overlapping or non-idempotent work still needs design-level protection.

Execution label. No Snowflake SQL ran. The graph state is a local JavaScript model.
