Understand the idea · 4 min

A guardrail prevents a car from leaving the road. A tow truck recovers it afterward. They solve different problems.

Days45–50 built preventive and detective controls: preserve bad rows, keep array position, inspect join plans, mask values, bind workload identity, and test the whole chain. Today adds a missing recovery control. After an accidental delete, first identify the last known-good table state. Restore or clone only after proving the target point and retention boundary.

A worked example

orders_silver had 1,000 rows. Statement delete-51 removed 880, leaving 120. The safe response is not “rerun everything.” Inspect history, verify the earlier state, create a recoverable copy where possible, reconcile counts, then choose the production cutover.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use history-based recovery when a governed Delta or Snowflake table was changed or dropped and the required historical files are still retained.

Practical example. A production cleanup job deletes 880 of 1,000 order rows; the incident team needs a verified pre-delete table state without replaying every upstream source.

How to decide. Prefer a historical clone for investigation when the product supports it. Restore in place only after impact, downstream readers, retention, permissions, and reconciliation are understood. Replay source data when history is unavailable or external effects also need repair.

9 minutes · product implementation

Databricks: inspect Delta history, then RESTORE to a proven version

First-minute product recall: Day28 distinguished identity from grants; Day45 preserved malformed evidence; Day47 required physical-plan evidence. None of those restores an accidental delete.

-- Databricks SQL; not executed in productDESCRIBE HISTORY orders_silver;SELECT count(*) FROM orders_silver VERSION AS OF 40;RESTORE TABLE orders_silver TO VERSION AS OF 40;

RESTORE creates another table version. It requires MODIFY. If files referenced by version 40 were removed manually or by VACUUM, a complete restore can fail.

Execution label. SQL was not executed in Databricks; the browser is a local teaching model.

9 minutes · product implementation

Snowflake: query before the statement, clone the historical table, then reconcile

First-minute product recall: Day28 separated authentication from authorization; Day45 separated validation from loading; Day48 applied query-time masking. Recovery is a separate retained-history decision.

-- Snowflake SQL; not executed in productSELECT count(*) FROM orders_silver BEFORE(STATEMENT => 'delete-51');CREATE TABLE orders_silver_recovered CLONE orders_silver  BEFORE(STATEMENT => 'delete-51');

Time Travel can query or clone a historical state within retention. Standard Edition defaults to one day; permanent objects on Enterprise Edition and above can be configured up to 90 days. UNDROP is for a dropped object, not an ordinary DELETE.

Execution label. SQL was not executed in Snowflake.
