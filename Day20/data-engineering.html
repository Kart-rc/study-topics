Understand the idea · 4 min

A paper receipt has one header and several item lines. JSON often uses the same shape: one order contains an items array. A semi-structured VARIANT keeps that nested shape. Flattening turns each array element into a correlated row.

Parse once, preserve the raw record, then project stable columns such as order_id, sku, and qty.

A worked example

Order R7 contains two items: two units of SKU A and one of SKU B. Switching to item rows repeats R7 while emitting two child rows. That repetition preserves the parent-child relationship.

A malformed payload is different from an empty array. Strict parsing stops it; tolerant parsing can quarantine it, but null must not silently mean “zero items.”

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this when producers add optional fields or nested arrays faster than a rigid ingestion schema can evolve.

Practical example. Land order JSON in a bronze table, retain the original VARIANT, then flatten items into a silver line-item table.

How to decide. Use VARIANT for genuine flexibility and typed columns for stable high-value fields. Flatten only needed paths because row counts can grow quickly.

9 minutes · product implementation

Databricks: parse VARIANT, then explode only items

Use case. Land changing order JSON without discarding new fields, then create an item-level silver projection.

Prepared real lab. Use an authorized non-production Databricks SQL warehouse or cluster and Unity Catalog schema. Use DBR 15.4 LTS or later for the documented VARIANT query path. The operator needs create/modify privileges and compute; selected compute incurs cost.

9-minute route. First minute: due product recall. Then predict R7 row counts, advance the SQL, and explain malformed-input handling.

The SQL is not run on Databricks. Buttons run a local JavaScript model.

CREATE TABLE study20.bronze_orders (raw VARIANT);INSERT INTO study20.bronze_orders SELECT parse_json('{"order_id":"R7","items":[{"sku":"A","qty":2},{"sku":"B","qty":1}]}');SELECT raw:order_id::STRING, item.value:sku::STRING, item.value:qty::INT FROM study20.bronze_orders, LATERAL variant_explode(raw:items) item;

Failure/fix. parse_json errors on malformed input; deliberately quarantine with raw bytes, optionally using try_parse_json. VARIANT has documented clustering and operation limits.

9 minutes · product implementation

Snowflake: correlate VARIANT with LATERAL FLATTEN

Use case. Keep a nested receipt in VARIANT and emit one relational row per item.

Prepared real lab. Use an authorized non-production Snowflake account, schema, and active warehouse. The role needs create/insert/select privileges; warehouse use costs credits.

9-minute route. First minute: due product recall. Then predict R7 rows, advance SQL, and distinguish null, empty array, and parse failure.

The SQL is not run on Snowflake. Buttons run a local JavaScript model.

CREATE TABLE study20.bronze_orders (raw VARIANT);INSERT INTO study20.bronze_orders SELECT PARSE_JSON('{"order_id":"R7","items":[{"sku":"A","qty":2},{"sku":"B","qty":1}]}');SELECT raw:order_id::STRING, item.value:sku::STRING, item.value:qty::INT FROM study20.bronze_orders, LATERAL FLATTEN(input => raw:items) item;

Failure/fix. PARSE_JSON rejects invalid JSON; TRY_PARSE_JSON can return SQL NULL. Recursive FLATTEN can multiply rows rapidly, so scope the path.
