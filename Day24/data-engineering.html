Understand the idea · 4 min

Imagine a concert usher who marks each ticket number as used. The same ticket can be scanned twice without admitting two people. But if someone changes the name printed on an already-used ticket, the usher still sees the same ticket number and refuses it.

File ingestion works similarly: the service remembers a file identity, usually its path/name. Duplicate notifications do not necessarily create duplicate loads. Replacing the contents at the same path is dangerous because the ingestion memory can still say “already seen.”

A worked example

The first event for orders/2026-10-14-18.json loads rows O-7 and O-8. A repeated event for that path is skipped. A corrected file uploaded to the same path can also be skipped. Uploading the correction as ...-18-v2.json gives it a new identity; downstream logic can then reconcile O-7 rather than blindly appending another order.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use managed file ingestion when producers land immutable files in object storage and the pipeline must recover from duplicate notifications or restarts.

Practical example. An S3 producer writes hourly order files. A notification is retried after a network timeout, and one batch later needs a correction.

How to decide. Treat source files as immutable, keep ingestion state durable, and publish corrections under a new path. Add business-key reconciliation because file-level exactly-once does not remove duplicates across different files.

9 minutes · product implementation

Databricks: Auto Loader remembers files in its checkpoint

Use case. Continuously ingest immutable JSON files from S3 into a Delta bronze table and resume after a job failure.

Prepared real lab. Use an authorized non-production workspace, external location and durable checkpoint. The SQL is unexecuted vendor practice; the visual below is a local teaching model.

CREATE OR REFRESH STREAMING TABLE bronze_ordersAS SELECT *, _metadata.file_path AS source_fileFROM STREAM read_files(  's3://acme-study/orders/', format => 'json');

Failure/fix. Reusing the same source path can hide a correction. Keep files immutable, use a new path, and use a downstream MERGE on business identity if the correction must replace earlier rows. A separate source should use a separate checkpoint.

9 minutes · product implementation

Snowflake: Snowpipe remembers loaded filenames for a limited window

Use case. Auto-ingest immutable staged CSV files into a landing table while tolerating duplicate cloud events.

Prepared real lab. Use an authorized non-production database, stage, integration and warehouse context. The SQL is unexecuted vendor practice; the visual is local JavaScript.

CREATE PIPE orders_pipe AUTO_INGEST=TRUE ASCOPY INTO bronze_ordersFROM @orders_stage FILE_FORMAT=(TYPE=CSV);SELECT * FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(  TABLE_NAME=>'BRONZE_ORDERS', START_TIME=>DATEADD('hour',-1,CURRENT_TIMESTAMP())));

Failure/fix. Snowpipe load metadata records file path/name for 14 days. The same filename can be ignored inside that window even if bytes changed; after metadata expires it can load again. Use immutable, versioned names and do not mix Snowpipe with bulk COPY for the same files unless duplication is deliberately controlled.
