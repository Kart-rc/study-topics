Understand the idea · 4 min

Imagine a supermarket. A wider checkout lane helps one shopper with a huge cart. Opening more lanes helps many shoppers who are waiting. Data warehouses have the same two controls: make a worker larger for a heavy query, or add workers/clusters for concurrency.

Do not resize first and ask why later. Look at the symptom: one query spills or runs slowly, or many otherwise healthy queries sit in a queue.

A worked example

At 09:00, one finance query needs 70 capacity units. At 10:00, twelve dashboard queries each need 10. A 40-unit worker cannot run the finance query efficiently; a single 80-unit worker can. But twelve dashboard requests still queue behind one another unless the service can add clusters.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this decision whenever a SQL endpoint is slow: first distinguish per-query pressure from concurrency pressure.

Practical example. A month-end reconciliation spills on one cluster, while the morning BI dashboard is fast once it starts but waits in a queue.

How to decide. Scale up for a query that cannot fit or parallelize well. Scale out for many independent queries waiting. Add auto-stop/suspend only after choosing the right capacity shape.

Databricks: warehouse size and cluster range answer different questions

Use case. A serverless SQL warehouse serves executive dashboards and a month-end reconciliation.

Unexecuted vendor practice. Configure an authorized SQL warehouse; the browser visual is local JavaScript.

-- Warehouse settings, not notebook SQL:Cluster size: 2X-Small → Medium  -- heavier queryScaling: min 1, max 4 clusters -- more concurrencyAuto stop: 10 minutes          -- idle cost

Failure/fix. Raising maximum clusters will not necessarily rescue one memory-heavy query. Increase warehouse size or tune the query for per-query pressure; raise cluster range for queued concurrency. Serverless behavior and limits vary by workspace and region.

9 minutes · product implementation

Snowflake: warehouse size versus multi-cluster concurrency

Use case. A reporting warehouse must run a large reconciliation and absorb a dashboard burst.

Unexecuted vendor SQL. Run only with change control. The browser visual is local JavaScript.

ALTER WAREHOUSE reporting SET WAREHOUSE_SIZE = LARGE;ALTER WAREHOUSE reporting SET  MIN_CLUSTER_COUNT = 1 MAX_CLUSTER_COUNT = 4  SCALING_POLICY = STANDARD AUTO_SUSPEND = 600;

Failure/fix. Resizing changes the resources of each cluster. Multi-cluster adds clusters for concurrency and requires the relevant Snowflake edition. Auto-suspend/resume controls idle use; verify caching and latency effects before shortening it.
