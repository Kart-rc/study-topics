Understand the idea · 4 min

Think of a library card. The library keeps one book; readers receive permission to read it. A shared table works the same way: the provider keeps the governed data and grants read access. The recipient queries the provider-owned data instead of receiving a frozen export.

This removes scheduled copy jobs, but it does not remove authorization, query cost, egress, schema-change risk, or the need to know who may see each row.

A worked example

The fraud team owns risk.daily_scores. A partner needs current scores for five regions. A nightly CSV is twelve hours stale and becomes an unmanaged copy. A share keeps one provider-owned table current; a dynamic view can expose only approved rows and columns.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use live sharing when another team or organization needs current governed data but should not own an independent extract pipeline.

Practical example. A bank shares daily risk scores with a claims partner while keeping the source table, policy and audit trail under provider control.

How to decide. Choose a live share when freshness and centralized revocation outweigh cross-region egress and provider coupling. Use a materialized export when the recipient needs isolation, offline processing or a stable historical snapshot.

Databricks: after enabling liquid clustering, what operation rewrites existing data layout in this lesson?

Recall first, then reveal the product refresher

OPTIMIZE (FULL for the explicit full rewrite shown). OPTIMIZE performs clustering work. FULL explicitly forces full reclustering on supported runtimes; VACUUM and grants solve different problems.

Snowflake: does a table need a user clustering key before any micro-partition pruning can occur?

Recall first, then reveal the product refresher

No; metadata is automatic, while a key can improve layout for suitable large tables. Snowflake records micro-partition metadata automatically. User clustering keys are selective optimizations and are unsupported for hybrid tables.

9 minutes · product implementation

Databricks: share a Unity Catalog object

Use case. Give a partner read access to a governed table without building a second ingestion pipeline.

Unexecuted vendor practice. Run only in an authorized workspace. The browser visual is a local model.

CREATE SHARE risk_partner;ALTER SHARE risk_partner ADD TABLE risk.daily_scores;CREATE RECIPIENT claims_partner;GRANT SELECT ON SHARE risk_partner TO RECIPIENT claims_partner;

Failure/fix. A long-lived bearer token can be copied. Prefer OIDC where supported, restrict recipients and views, rotate credentials, audit reads, and account for cross-region egress. Databricks-to-Databricks sharing uses Unity Catalog identities instead of a recipient bearer token.

9 minutes · product implementation

Snowflake: a share becomes a read-only imported database

Use case. Share selected database objects with another Snowflake account without copying their storage.

Unexecuted vendor practice. Use an authorized provider and consumer account. The browser visual is local JavaScript.

CREATE SHARE risk_partner;GRANT USAGE ON DATABASE risk TO SHARE risk_partner;GRANT SELECT ON TABLE risk.public.daily_scores TO SHARE risk_partner;ALTER SHARE risk_partner ADD ACCOUNTS = consumer_org.consumer;-- consumer: CREATE DATABASE risk_shared FROM SHARE provider_org.provider.risk_partner;

Failure/fix. The imported database is read-only; the consumer pays query compute while the provider keeps storage. One share is associated with one database. Use secure views or database roles to narrow exposure; use reader accounts for consumers without Snowflake accounts.
