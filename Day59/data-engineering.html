Understand the idea · 4 min

A deli ticket tells the cook which order comes next. A tray size tells the cook how many sandwiches to carry. One remembers position; the other limits work.

Streaming ingestion needs both ideas. A checkpoint or committed offset remembers durable progress after a crash. A batch-size or client-capacity control bounds how much work enters the next processing interval. Raising the limit can drain a backlog faster, but it does not make progress durable. Deleting progress state can make the system repeat or miss work.

A worked example

Source receipts-59 has 2,500 files. A hard limit of 1,000 files produces batches of 1,000, 1,000, and 500. The checkpoint advances after each committed batch. If batch two fails before commit, recovery resumes from the batch-one checkpoint—not from the configured limit.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use separate progress and capacity controls when a stream has a backlog or bursty arrivals.

Practical example. A retail data platform must catch up after an object-store notification outage without replaying already committed receipts.

How to decide. Preserve durable progress first. Tune batch or client capacity from memory, latency, cost, and downstream evidence. Never use state expiry as a casual throughput knob.

Databricks: bound Auto Loader work without weakening its checkpoint

First-minute product recall: Complete the scheduled product refresher above.

-- SQL sketch; not executed in DatabricksCREATE OR REFRESH STREAMING TABLE bronze_receiptsAS SELECT * FROM STREAM read_files('/receipts-59',  format => 'json', maxFilesPerTrigger => 1000);

Auto Loader records discovered-file progress in its checkpoint. The documented default is at most 1,000 files per micro-batch; cloudFiles.maxFilesPerTrigger is a hard file limit, while cloudFiles.maxBytesPerTrigger is soft. Keep checkpoints away from lifecycle deletion. Aggressive maxFileAge can cause ignored or reprocessed files.

9 minutes · product implementation

Snowflake: offset tokens prove channel progress; they do not size the client

First-minute product recall: Complete the scheduled product refresher above.

-- Validation SQL; not executed in SnowflakeSELECT COUNT(*) FROM bronze_receiptsWHERE source_partition = 'p59';# SDK sketch: appendRows(rows, offsetToken='1000')# reopen channel; resume after latest committed token

Snowpipe Streaming persists an application-supplied offset token with committed rows on a named channel. On reopen, read the latest token and replay retained source data after it. This is not a direct equivalent of Auto Loader's per-micro-batch file limit: client batching, channels, buffering, and source retention control capacity. High-performance channels can be cleared after 30 days without ingestion, so keep a separate offset when that matters.
