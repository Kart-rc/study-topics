## Understand (4 minutes)

Suppose three services reject order O42. One returns {"error":"no stock"}, another returns {"message":"failed"}, and the third returns an HTML page. Every client needs custom parsing.

RFC 9457 defines a common envelope called Problem Details. The HTTP status keeps its normal meaning. The body adds a stable problem type, a short title, occurrence-specific detail, and an instance identifier.


HTTP409 Conflict

type/problems/out-of-stock

instance/errors/e-731

Branch on stable type; show detail to a person; trace one occurrence by instance.



For order O42, the response can use Content-Type: application/problem+json:

{
  "type": "https://api.example/problems/out-of-stock",
  "title": "Item is out of stock",
  "status": 409,
  "detail": "SKU-7 cannot fulfill order O42",
  "instance": "/errors/e-731",
  "sku": "SKU-7"
}

A client branches on the stable type URI, not on the human sentence in detail. The status member is advisory and must match the actual HTTP response status generated by the origin server.



## Use case: when to use this

Part of the 4-minute explanation.

**When it fits.** Use Problem Details when multiple HTTP clients need consistent error handling across APIs, especially when the status code alone does not explain the action a client should take.

**Practical example.** In this lesson, order O42 returns HTTP 409 with the out-of-stock type so the client can ask for another item. In a data-platform API, a proposed rule-name-conflict type could tell the UI to ask for a new name while instance identifies the specific failed request for support.

**How to decide.** Agree on stable type meanings and document them in the API contract. Keep sensitive internals out of detail. An ordinary HTTP status may be enough when clients need no additional distinction; the envelope does not choose a safe retry policy for you.


## Step through the code (within the 5-minute exploration)

Spend about two minutes here and three in the interactive lab. These are actual recorded executions of the synthetic example, replayed in the HTML page.

```python
failure = 'out_of_stock'
order_id = 'O42'
occurrence = 'e-731'
problem = {
    'type': 'https://api.example/problems/out-of-stock',
    'title': 'Item is out of stock',
    'status': 409,
}
problem['detail'] = f'SKU-7 cannot fulfill order {order_id}'
problem['instance'] = f'/errors/{occurrence}'
http_status = 409
content_type = 'application/problem+json'
client_action = 'change item' if problem['type'].endswith('out-of-stock') else 'inspect'
status_matches = http_status == problem['status']
```

1. Start with one domain failure and one specific occurrence.

   Changed values: `{"failure": "out_of_stock", "order_id": "O42", "occurrence": "e-731"}`

2. Use a stable type for machines, a short title for people, and the normal HTTP status.

   Changed values: `{"problem": {"type": "https://api.example/problems/out-of-stock", "title": "Item is out of stock", "status": 409}}`

3. Add occurrence-specific explanation and an opaque support identifier.

   Changed values: `{"problem": {"type": "https://api.example/problems/out-of-stock", "title": "Item is out of stock", "status": 409, "detail": "SKU-7 cannot fulfill order O42", "instance": "/errors/e-731"}}`

4. The client branches on type, while the transport and body statuses remain consistent.

   Changed values: `{"http_status": 409, "content_type": "application/problem+json", "client_action": "change item", "status_matches": true}`

## Quiz (4 minutes)

1. Which field should machine logic use as the primary problem identifier?
   - The type URI
   - A substring inside detail
   - The title’s punctuation

2. What if the body says status 409 but the actual response is HTTP 500?
   - That disagreement is unsafe; generic software follows the HTTP response
   - The body always overrides HTTP
   - Both statuses are ignored

3. What is a security boundary?
   - Do not expose stack traces or sensitive internals in problem details
   - Put database credentials in detail
   - Require clients to dereference every type URI

4. Design one stable problem type for a data-platform API and identify the client action it enables.
5. When is an ordinary HTTP status sufficient without a Problem Details body?

<details><summary>Answer key — attempt first</summary>

1. The type URI. RFC 9457 defines type as the primary problem identifier; detail is human-readable.

2. That disagreement is unsafe; generic software follows the HTTP response. The status member is advisory and generators must use the same actual response status.

3. Do not expose stack traces or sensitive internals in problem details. Problem details describe the HTTP interface, not internal debugging state.
