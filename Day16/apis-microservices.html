Understand the idea · 4 min

Suppose three services reject order O42. One returns {"error":"no stock"}, another returns {"message":"failed"}, and the third returns an HTML page. Every client needs custom parsing.

RFC 9457 defines a common envelope called Problem Details. The HTTP status keeps its normal meaning. The body adds a stable problem type, a short title, occurrence-specific detail, and an instance identifier.

Visual question: Which response fields serve the client, the reader, and the trace?

A worked example

For order O42, the response can use Content-Type: application/problem+json:

{
  "type": "https://api.example/problems/out-of-stock",
  "title": "Item is out of stock",
  "status": 409,
  "detail": "SKU-7 cannot fulfill order O42",
  "instance": "/errors/e-731",
  "sku": "SKU-7"
}

A client branches on the stable type URI, not on the human sentence in detail. The status member is advisory and must match the actual HTTP response status generated by the origin server.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use Problem Details when multiple HTTP clients need consistent error handling across APIs, especially when the status code alone does not explain the action a client should take.

Practical example. In this lesson, order O42 returns HTTP 409 with the out-of-stock type so the client can ask for another item. In a data-platform API, a proposed rule-name-conflict type could tell the UI to ask for a new name while instance identifies the specific failed request for support.

How to decide. Agree on stable type meanings and document them in the API contract. Keep sensitive internals out of detail. An ordinary HTTP status may be enough when clients need no additional distinction; the envelope does not choose a safe retry policy for you.

What this code proves—and what it leaves out

Optional deeper explanation and original worked example

RFC 9457 replaced RFC 7807 in July 2023. It defines application/problem+json, the standard members, extension behavior, and security considerations. Unknown extensions must be ignored. A resolvable type URI is encouraged, but clients should not automatically dereference it during normal handling.

Which response fields serve the client, the reader, and the trace? The response envelope is separated by responsibility. Stable type directs program behavior, detail explains this occurrence to a person, and instance identifies its trace. HTTP status remains the transport-level signal. The routing shown is this application’s policy.

What this model does and does not represent
Problem Details is an error envelope, not a distributed tracing system, retry policy, validation framework, or debugging dump. Do not leak stack traces or sensitive data. Clients must ignore unknown extensions. The actual HTTP status still controls generic intermediaries; a disagreeing body status is unsafe.
