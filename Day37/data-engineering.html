Understand the idea · 4 min

A parcel disappears. Replacing the truck will not help if the real problem is a locked loading dock, a rejected label, the wrong customer shelf, an expired tracking bookmark, or a test copy that still depends on the original box.

Data incidents often look alike from the dashboard. Diagnose the boundary that stopped preserving truth before changing pipeline code: identity, schema, row policy, change position, or clone dependency.

A worked example

The same synthetic order O-42 from Day36 now produces one of five symptoms. An S3 read returns access denied. A new coupon_code is absent from the published table. Tenant beta can see an acme row. Fulfillment misses changes after downtime. A QA clone fails after source files or policy dependencies change.

Each symptom points to a different first inspection. A retry is useful only after the failed boundary is known.

Use case: when to use this

Part of the 4-minute explanation.

When it fits. Use this retrieval map during incident triage, certification practice, design reviews, and post-release checks for governed incremental pipelines.

Practical example. An on-call engineer sees missing fulfillment updates after a weekend outage and must decide whether to inspect cloud access, schema rescue data, tenant policy, the change cursor, or clone dependencies.

How to decide. Start with the earliest boundary whose evidence contradicts the expected state. Collect read-only evidence first. Do not infer a personal knowledge gap from this generated exercise; use submitted answers and authorized product labs to decide what needs more study.

9 minutes · product implementation

Databricks retrieval: separate access, schema, policy, cursor, and clone evidence

One incident, five evidence locations. Access denial starts at the storage credential and external-location path. A missing field starts at Auto Loader schema history and rescued data. Wrong rows start at the effective identity and row filter. Missing changes start at the CDF starting version and checkpoint. A broken shallow clone starts at its source-file dependency.

-- sourced diagnostic sketches; not executed hereDESCRIBE HISTORY ops.orders_internal;SELECT * FROM table_changes('ops.orders_internal', :from_version);DESCRIBE DETAIL qa.orders;

Failure/fix. If the requested CDF history is gone, a retry cannot recreate it. Reconcile from an authoritative snapshot or other retained source, reset the consumer position deliberately, and document the gap. If automatic CDF conflicts with row filters, split the internal change surface from filtered serving.

9 minutes · product implementation

Snowflake retrieval: read the Stream clock and policy context before recreating anything

Start with the Stream state. A Stream becomes stale when its offset falls outside retained history. SHOW STREAMS exposes STALE and STALE_AFTER. Recreating the Stream resumes future tracking; it does not by itself recover the missed interval. Wrong row visibility is a separate policy-context problem. A clone can also have policy references or historical-change boundaries that differ from the source.

-- sourced diagnostic sketches; not executed hereSHOW STREAMS LIKE 'ORDERS_DELTA';SELECT SYSTEM$STREAM_HAS_DATA('ORDERS_DELTA');-- reconcile missed rows before CREATE OR REPLACE STREAM

Failure/fix. Consume before STALE_AFTER and monitor the clock. After staleness, preserve the gap question, reconcile from retained authoritative data where possible, then recreate the Stream for future changes.
